01. Konsep Dasar VCS
02 / 20

Mengapa Kita Butuh Version Control System?

Sebelum mengenal Git, bagaimana cara developer menyimpan perubahan dokumen proyek mereka? Masalah klasik ini sering berujung bencana.

Manajemen Manual (Tanpa Git)
📁 web-portfolio/
├── index.html
├── index_final.html
├── index_final_banget.html
├── index_final_revisi_bos.html
└── index_final_fix_bismillah.zip

Risiko: Tidak tahu apa yang berubah di setiap file, mudah tertimpa tanpa sengaja, dan mustahil mengembalikan versi lampau jika ada bug.

Manajemen Modern (Dengan Git)
$ git log --oneline
e4b1a09 feat: add responsive navbar
9f2c810 fix: resolve hero layout overflow
1a7d422 feat: initial project structure

Keunggulan: Struktur file tetap rapi, setiap snapshot riwayat tercatat siapa yang mengubah, kapan diubah, dan mengapa diubah. Bisa time-travel kapan saja!

Definisi Git: Git adalah Distributed Version Control System (DVCS) open-source yang merekam perubahan file dalam bentuk Snapshot (bukan sekadar perbedaan teks delta), memungkinkan ribuan developer bekerja pada satu basis kode secara paralel tanpa saling merusak.
02. Arsitektur Git
03 / 20

Arsitektur 3 Wilayah Utama Git

Kunci terbesar memahami Git adalah mengetahui di wilayah mana file kamu sedang berada saat proses modifikasi berlangsung.

1. Working Directory
Folder proyek fisik di komputermu (VS Code).
index.html Modified
style.css Untracked
Perubahan belum diamankan Git
2. Staging Area (Index)
Ruang persiapan sebelum dibuat commit.
index.html Staged
Ditambahkan via git add
3. Git Local Repo
Database riwayat commit tersimpan di .git.
commit: #e4b1a09
commit: #1a7d422
Tersimpan via git commit
4. Remote Repository
Penyimpanan cloud bersama (GitHub/GitLab).
origin/main Synced
Terkirim via git push
Siklus Status File (File Lifecycle)

• Untracked: File baru yang belum pernah dicatat oleh Git.
• Modified: File yang sudah ada sebelumnya, lalu diubah isinya.
• Staged: File yang ditandai untuk dimasukkan ke snapshot berikutnya.
• Committed: File sudah tersimpan aman di database Git lokal.

Mengapa Harus Lewat Staging Area?

Staging Area memberi kita kontrol penuh untuk memilah: kamu bisa mengedit 5 file berbeda, namun hanya memilih 2 file terkait untuk dijadikan satu commit yang rapi dan terisolasi!

03. Setup Awal
04 / 20

Setup Awal & Konfigurasi Identitas Git

Sebelum membuat commit pertama, Git wajib mengetahui siapa kamu agar setiap rekaman jejak tercantum nama dan email penulis aslinya.

Terminal / Bash Konfigurasi Global
# 1. Atur nama identitas kamu $git config --global user.name "Fahmi Ilham" # 2. Atur alamat email (gunakan email yang terdaftar di akun GitHub) $git config --global user.email "fahmi@itsenja.com" # 3. Tetapkan nama branch default standar industri modern $git config --global init.defaultBranch main # 4. Periksa seluruh daftar konfigurasi yang aktif $git config --list
Opsi --global

Konfigurasi berlaku untuk semua proyek di komputer kamu. Hanya perlu dijalankan 1 kali saja saat instalasi.

Autentikasi GitHub: PAT

GitHub tidak lagi mengizinkan password akun untuk push kode via CLI. Gunakan Personal Access Token (PAT).

Opsi Modern: SSH Key

Setup SSH key (ssh-keygen -t ed25519) untuk otentikasi otomatis yang aman tanpa memasukkan password berulang.

04. Siklus Dasar
05 / 20

Siklus Fundamental: Init, Status, Add, & Commit

Empat perintah ini adalah denyut nadi utama yang akan kamu gunakan ratusan kali setiap hari saat mengembangkan website.

1. git init & git status

• git init: Mengaktifkan folder biasa menjadi Git repository dengan membuat subfolder tersembunyi .git/.
• git status: Kompas navigator kamu untuk melihat file mana yang diubah, mana yang sudah di-stage, atau belum terlacak.

$git init Initialized empty Git repository in /project/.git/ $git status
2. git add & git commit

• git add index.html: Memasukkan 1 file tertentu ke Staging Area.
• git add .: Memasukkan semua perubahan di direktori saat ini ke Staging.
• git commit -m "pesan": Membungkus staging menjadi satu snapshot permanen.

$git add . $git commit -m "feat: create landing page structure"
Aturan Emas (Atomic Commit): Satu commit harus menyelesaikan satu tugas logis. Hindari menumpuk 10 fitur dalam satu commit tunggal raksasa. Commit kecil dan sering jauh lebih mudah di-review dan aman di-rollback jika bermasalah!
05. Standar Industri
06 / 20

Standar Pesan Commit: Conventional Commits

Di industri profesional, menulis pesan commit seperti "update", "fix bug", "bismillah" dilarang keras. Gunakan standar format baku yang rapi dan mudah dibaca oleh tim serta sistem otomatisasi.

<type>[optional scope]: <description in imperative tense>
feat:

Menambahkan fitur baru untuk pengguna.
Contoh: feat: add dark mode switch

fix:

Memperbaiki bug atau kesalahan tampilan.
Contoh: fix: resolve mobile navbar overlap

docs:

Perubahan pada dokumentasi saja (README).
Contoh: docs: update deployment guide

refactor:

Merombak kode tanpa mengubah fungsi luar.
Contoh: refactor: simplify fetch promise

style:

Format kode, spasi, titik koma (tanpa ubah logika).
Contoh: style: format css indentation

chore:

Konfigurasi build, dependencies, atau docker.
Contoh: chore: update nginx config

07. Inspeksi Riwayat
08 / 20

Membaca Jejak: Git Log & Git Diff

Mengetahui apa yang telah terjadi dan apa yang sedang berubah adalah kunci utama debugging dan kolaborasi yang tenang.

git log — Riwayat Snapshot

Perintah git log menampilkan daftar lengkap siapa pembuat commit, tanggal pembuatan, pesan, dan kode hash unik SHA-1.

Paling Sering Digunakan di Tim
# Tampilan ringkas 1 baris per commit $git log --oneline # Tampilan visual grafik percabangan $git log --oneline --graph --all
git diff — Selisih Baris Kode

Melihat baris mana yang dihapus (warna merah tanda -) dan baris mana yang baru ditambahkan (warna hijau tanda +).

Pemeriksaan Sebelum Staging
# Periksa editan di working directory $git diff # Periksa editan yang SUDAH di-stage $git diff --staged
Anatomi Commit Hash: Setiap commit memiliki ID unik 40 karakter hex (SHA-1), misalnya e4b1a09d3f1a2c.... Untuk referensi perintah Git, kita cukup menuliskan 7 karakter awalnya saja (misal: e4b1a09).
08. Proteksi Kode
09 / 20

Mengabaikan File Sensitif: File .gitignore

Tidak semua file harus masuk ke Git. File rahasia, kredensial server, atau folder dependensi raksasa wajib diabaikan agar repositorimu aman dan ringan.

File yang Wajib Diabaikan:
  • File Rahasia & Kredensial: .env, API keys, password, token JWT.
  • Dependensi Berat: node_modules/, folder vendor/.
  • File Sistem Operasi: .DS_Store (macOS), Thumbs.db (Windows).
  • Hasil Build: Folder dist/, build/, file *.log.
Kasus Fatal di Industri: Meng-upload file .env berisi API key OpenAI atau AWS ke GitHub publik dapat menyebabkan tagihan ratusan juta rupiah dalam hitungan menit akibat bot pencuri kunci!
Contoh Isi File .gitignore
# 1. Dependensi node_modules/ # 2. File Lingkungan & Kunci Rahasia .env .env.local *.key # 3. File Log Sistem *.log # 4. Folder Build Sementara dist/ tmp/
Jika file sudah terlanjur ter-track, lepaskan dengan: git rm --cached <file>
09. Pembatalan Aman
10 / 20

Time Travel & Pembatalan: Undo & Reset Workflow

Melakukan kesalahan saat menulis kode adalah hal wajar. Git menyediakan berbagai tingkat penyelamatan tergantung di mana kesalahan terjadi.

1. Batalkan di Working Tree

Kamu mengedit file, tapi ingin membatalkan semua editan tersebut dan kembali ke versi commit terakhir:

$git restore index.html
2. Batalkan dari Staging

File terlanjur dimasukkan lewat git add, tapi kamu ingin mengeluarkannya dari antrean staging:

$git restore --staged index.html
3. Tambal Commit Terakhir

Lupa memasukkan file atau salah ketik pesan di commit terakhir yang baru saja dibuat:

$git commit --amend -m "pesan benar"
git revert <hash> (Pilihan Paling Aman!)

Membuat commit baru yang membalikkan efek dari commit masa lalu tanpa menghapus riwayat. Sangat aman digunakan pada branch yang sudah di-share ke GitHub bersama tim.

git reset --hard (Gunakan dengan Waspada)

Menghapus commit dan membuang semua perubahan file secara permanen. Jangan pernah gunakan opsi ini pada branch publik atau jika belum yakin!

10. Percabangan
11 / 20

Strategi Percabangan: Branching Workflow

Branch memungkinkan kamu membuat ruang kerja terisolasi untuk fitur baru tanpa mengganggu kode utama yang sedang berjalan stabil di produksi.

Perintah Esensial Branch
# 1. Lihat semua branch lokal $git branch # 2. Buat branch baru & langsung pindah ke sana $git switch -c feature/navbar-responsive # (atau perintah klasik: git checkout -b feature/navbar) # 3. Pindah kembali ke branch main $git switch main # 4. Hapus branch yang sudah selesai di-merge $git branch -d feature/navbar-responsive
Konvensi Penamaan Branch Profesional
• feature/<nama-fitur>: Pembuatan fitur baru (misal: feature/login-modal)
• bugfix/<nama-bug>: Perbaikan error non-kritis (misal: bugfix/typo-header)
• hotfix/<nama-bug>: Tambalan darurat langsung pada server produksi
• refactor/<nama>: Restrukturisasi arsitektur kode
Golden Rule: Jangan pernah mengetik kode fitur baru langsung di branch main. Buat branch fitur terlebih dahulu!
11. Penggabungan
12 / 20

Penggabungan Cabang: Fast-Forward vs 3-Way Merge

Setelah pengerjaan di branch fitur selesai dan teruji rapi, saatnya menggabungkan kembali perubahannya ke dalam branch utama (main).

1. Fast-Forward Merge

Terjadi ketika branch main belum memiliki commit baru sama sekali sejak branch fitur dibuat. Git cukup memajukan pointer main ke commit terdepan.

main: (A) ───► (B) [Fast-Forward ke C]
feature: └──► (C)
2. 3-Way Merge (Merge Commit)

Terjadi jika branch main dan branch fitur masing-masing memiliki commit baru tersendiri. Git akan membuat satu commit penyatu otomatis khusus.

main: (A) ───► (B) ──────► (M: Merge Commit)
feature: └──► (C) ───┘
Langkah Baku Melakukan Merge
# Langkah 1: Pindah ke branch tujuan (biasanya main) $git switch main # Langkah 2: Satukan perubahan dari branch fitur $git merge feature/navbar-responsive # Langkah 3: Hapus branch fitur yang sudah terintegrasi $git branch -d feature/navbar-responsive
12. Conflict Resolver
13 / 20

Menghadapi & Menyelesaikan Merge Conflict

Merge conflict terjadi jika dua branch memodifikasi baris kode yang sama pada file yang sama. Git tidak bisa menebak versi mana yang benar, sehingga meminta kamu menentukannya.

File: index.html (Conflict State) Konflik Belum Selesai
<!-- CONFLICT REGION -->
<<<<<<< HEAD (Branch main) <h1 class="hero-title">Belajar Web Modern dengan Bootcamp ITSENJA</h1>
=======
>>>>>>> feature/update-hero (Incoming Branch) <h1 class="hero-title">Kuasai Web Development dari Nol hingga Mahir</h1>
<p class="subtitle">Kurikulum komprehensif HTML5, CSS3, JS & Git.</p>
Langkah Manual di VS Code: Edit file hingga tanda <<<<<<<, =======, dan >>>>>>> bersih, lalu jalankan git add index.html dan git commit -m "fix: resolve merge conflict on hero title".
13. Parkir Sementara
14 / 20

Git Stash: Simpan Sementara Tanpa Commit

Bayangkan kamu sedang di tengah-tengah menulis fitur baru (kode masih berantakan), tiba-tiba mentor/bos memintamu segera memperbaiki bug mendadak di branch lain.

Konsep Laci Penyimpanan (Stash)

git stash mengambil semua perubahan di working directory dan menyimpannya ke dalam "laci rahasia". Direktori kamu seketika kembali bersih seperti commit terakhir, sehingga kamu bisa berpindah branch dengan aman tanpa terhalang error.

Setelah tugas darurat selesai, cukup jalankan git stash pop untuk mengembalikan semua pekerjaan yang sempat diparkir!
Perintah Esensial Stash
# 1. Simpan perubahan dengan catatan deskripsi $git stash save "setengah jadi bikin form" # 2. Lihat daftar laci simpanan yang tersimpan $git stash list # 3. Ambil kembali editan & buang dari laci $git stash pop # 4. Hapus seluruh isi laci stash $git stash clear
14. Remote Repository
15 / 20

Sinkronisasi Cloud: Bekerja dengan GitHub

Remote repository adalah salinan repositorimu yang tersimpan di internet (GitHub, GitLab) untuk tujuan pencadangan awan dan kolaborasi tim.

Alur Menghubungkan Repo Lokal ke GitHub
# 1. Daftarkan URL GitHub sebagai remote alias bernama 'origin' $git remote add origin https://github.com/USERNAME/web-portfolio.git # 2. Verifikasi alamat remote yang sudah terdaftar $git remote -v # 3. Unggah seluruh commit pertama ke GitHub (-u menetapkan upstream tracking) $git push -u origin main # 4. Ambil pembaruan terbaru yang di-push oleh rekan tim $git pull origin main
Apa itu origin?

Nama panggilan default (alias) untuk URL server remote utamamu agar tidak perlu mengetik URL panjang berulang-ulang.

Opsi -u (Upstream)

Menghubungkan branch lokal main dengan remote origin/main, sehingga pada push berikutnya cukup ketik git push.

git pull = Fetch + Merge

Mengunduh commit baru dari cloud sekaligus menggabungkannya secara otomatis ke branch lokal aktifmu.

15. Kolaborasi Tim
16 / 20

Kolaborasi Tim: Pull Request & Code Review

Di perusahaan teknologi, developer tidak pernah langsung meng-push kode ke branch main. Semua perubahan wajib melewati proses Pull Request (PR) dan review oleh tim.

1
Buat Branch

Developer membuat feature branch lokal & push ke GitHub.

2
Buka PR di GitHub

Jelaskan fitur apa yang dibuat, sertakan screenshot dan issue.

3
Code Review

Senior/Rekan menguji baris kode, memberi komentar atau masukan.

Merge to Main

Setelah disetujui (Approved), PR di-merge ke branch main.

Etika Menulis Pull Request yang Baik:
  • Gunakan judul yang jelas sesuai Conventional Commits.
  • Jelaskan masalah apa yang diselesaikan dan cara mengujinya.
  • Sertakan tangkapan layar jika ada perubahan visual antarmuka.
  • Jaga agar ukuran PR tidak terlalu besar (< 300 baris kode).
Opsi Merge di GitHub:
  • Create a merge commit: Menyimpan seluruh commit riwayat cabang.
  • Squash and merge: Menggabungkan 10 commit fitur menjadi 1 commit rapi di main (Sangat direkomendasikan!).
  • Rebase and merge: Memindahkan commit secara linier.
16. Deployment Otomatis
17 / 20

Deployment Workflow: Website Live di Internet!

Tujuan akhir seorang web developer adalah menerbitkan karyanya ke internet agar dapat diakses oleh siapapun dengan tautan publik.

1. GitHub Pages (Gratis) Untuk Website Statis

Sangat cocok untuk portofolio HTML, CSS, dan JavaScript tanpa perlu menyewa VPS.

1. Buka repo GitHub kamu > klik tab Settings.
2. Di menu kiri, pilih Pages.
3. Pada Source, pilih Deploy from a branch.
4. Pilih branch main dan folder / (root) > Save.
5. Website kamu live di: https://username.github.io/repo/!
2. Vercel (Auto CI/CD) Industri Standar

Platform cloud modern dengan fitur Continuous Deployment otomatis.

1. Login di vercel.com menggunakan akun GitHub.
2. Klik Add New... > Project > pilih repositori portofoliomu.
3. Klik tombol Deploy (langsung aktif dengan SSL HTTPS gratis!).
4. Keajaiban CI/CD: Setiap kali kamu menjalankan git push, Vercel otomatis meng-update website dalam 10 detik!
Hasil Akhir: Sertakan tautan live demo GitHub Pages / Vercel di CV atau profil LinkedIn kamu agar calon perekrut kerja dapat langsung mencoba karyamu!
